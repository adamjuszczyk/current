# CONTEXT.md — Current

## What this is
Current — a personal project/direction-tracking app. V1 shipped and is in real daily use; v2 is specced and planned against what that use showed. This file is the single source of truth for current app state; keep it lean and update it after every session, per usual convention.

## Stack
React, TypeScript, Vite, Tailwind, Supabase, TanStack Query, Zustand, Dexie, Recharts, vite-plugin-pwa.

## Database
Fresh, dedicated Supabase project. No shared backend or cross-app data access with Overload.

## Current build target
**V2 sandbox.** Spec: `CURRENT-V2-SANDBOX-SPEC.md`. Plan: `TASKS.md`. Still a sandbox, still no visual design pass — but no longer a guess: every feature in it traces to a specific instance of using v1 for real, which is exactly what v1 was built to produce.

Scope: what a Block contains is replaced by a project canvas inside a resizable popup, holding Lists (step-by-step or flat) and Notes; Connect adds block-to-block connections with graph auto-layout; Waiting adds project-level blocking built from entries, with a derived Ready state; Focused marks what's being worked on and gets its own screen; a three-way Filter controls what the canvas shows; and Visuals carry the states that aren't otherwise legible. Plus the one v1 fix: text inputs that expand with their content.

Carried forward from v1 unchanged: Areas, single-account auth with RLS, confirmation on every delete, Area-level Free Notes, one kind of Block, and the three manual statuses.

**Not in scope for this build:** Vision, Phase and everything on it, theming, any visual design pass, task-level Waiting, shared tasks between blocks, "Today", an explicit next-step pointer, projects-within-projects, zoom/pan, and fullscreen/tab mode. A fuller v2+/vision-scale version of this product exists, but is kept outside this repo on purpose, so it can't shape this build. It is not present here — don't look for it, don't reconstruct it, and its absence is not a gap to flag or escalate. Everything needed for this build is already in `CURRENT-V2-SANDBOX-SPEC.md`.

`CURRENT-V1-SANDBOX-SPEC.md` and `TASKS-V1.md` are kept as the record of what v1 was built to. The v2 spec supersedes the v1 spec entirely; neither v1 file is the plan of record any more.

- `scripts/verify-rls.mjs` (`npm run verify:rls`) exercises the Phase 0.3 acceptance criterion directly against the live project once `.env` is filled in: reads and writes all four tables with the anon key and no session, and fails loudly if any row is returned or any write succeeds.

Always read as a flat, unordered list (`order('created_at', ...)` for stable rendering only — no ordering column exists or is exposed). `useUpdateTask` covers both inline text edits and the complete-toggle, since both are just a partial update to the same row.
- `src/lib/blocks.ts` — added `useUpdateBlock` (name and/or status) and `useDeleteBlock`. Status is only ever written here, from an explicit user action; nothing reads task completion to decide it. `useDeleteBlock` only removes the `blocks` row — its Tasks are left to the migration's `on delete cascade`, same reasoning as Area delete not hand-deleting Blocks/Notes.
- `src/components/BlockEditPopup.tsx` — the one popup for 4.1-4.5, opened by double-clicking a Block. Name is a single input that commits on blur or Enter (no Save button — the popup stays open afterward so status and tasks can keep being edited in the same session, unlike `AreaEditPopup` which closes on submit). Status is three plain buttons (Upcoming/Active/Done), the current one highlighted; clicking one is the only way it ever changes. Tasks render as a flat list (`TaskRow`, a local component in the same file) — checkbox to toggle complete, an inline text input that commits on blur/Enter, and a Delete button gated by `useConfirm()`. An "Add a task" form at the bottom of the list appends new ones; there is no drag handle, order control, or up/down affordance anywhere in the list. Delete block is gated by `useConfirm()` too, and closes the popup on confirm.
- `src/components/BlockCard.tsx` — added double-click-to-open without touching the existing pointer-based drag (3.2). Native `dblclick` wasn't used: `setPointerCapture` keeps every pointer event routed to the block regardless of how far the cursor actually travelled, so the browser would still fire a `dblclick` after two real drags done in quick succession over the same block. Instead, `handlePointerUp` measures the distance travelled since `pointerdown`: over a small threshold (4px) it's a drag — position is persisted as before, and a click-timer ref is cleared so it can never combine with anything into a double-click; at or under the threshold it's a click, and if a prior click landed within 400ms it counts as a double-click and opens `block-edit` via the `uiStore` `openPopup`/`popupContext` pattern (same as `AreaTabs`/`Canvas` already use). A real drag can now never open the popup, and a double-click (near-zero movement on both clicks) can never displace the block, since the existing "only write x/y if it actually changed" guard from the Phase 3 post-review fix still applies to the drag path.
- `src/components/Canvas.tsx` — renders `BlockEditPopup` when `activePopup === 'block-edit'`, reading `blockId`/`areaId` out of `popupContext`, same shape as the existing `block-create` wiring.
- No new dependencies. No schema changes — the `tasks` table already had everything 4.1-4.5 needed; nothing here needed an ordering column, and none was added.
- Verified in a headless browser against a temporary in-memory mock of the Supabase client (written over `src/lib/supabase.ts`, restored before committing, same pattern as every prior phase) seeded with one Area, one Block, and two Tasks (one already complete): a real drag (mouse down, move 100px/80px, up) moved the block and did not open the popup; a double-click (two zero-movement clicks under 400ms apart) opened it without moving the block; renaming via the input and blurring persisted the new name (confirmed the input still showed it, and it survived reopening the popup); clicking Active then Done then Upcoming each re-highlighted the corresponding button and correspondingly changed the card's background behind the popup (blue for Active, dimmed grey for Done/Upcoming, matching 3.4); with status set to Active, checking both existing tasks' checkboxes complete left Active still highlighted — no automatic move to Done; typing into "Add a task" and pressing Enter appended a third task row; editing that row's text and blurring persisted the new text; toggling its checkbox checked it and applied the strikethrough style; clicking a task's Delete opened the confirm dialog naming that task, Cancel left it in the list, Delete-then-Confirm removed it; clicking "Delete block" opened the confirm dialog naming the block and mentioning its tasks, Cancel left the popup open with the block intact, Delete-then-Confirm closed the popup and removed the block from the canvas (now empty, matching the mock's cascade of its tasks). ### Phase 5 — what was built

- `src/types.ts` — `Note` row type added, mirroring `supabase/migrations/0001_init.sql` (untouched — no schema changes this phase; the table already had everything needed).
- `src/lib/notes.ts` — `useNotes(areaId)`, `useCreateNote`, `useUpdateNotePosition`, `useUpdateNoteContent`, `useDeleteNote`, same TanStack Query pattern as `src/lib/blocks.ts`. `useCreateNote` inserts an empty-content row immediately (5.1 — no popup). Position and content are separate mutations, mirroring how Blocks split position (`useUpdateBlockPosition`) from other edits (`useUpdateBlock`). `useDeleteNote` is the one mutation behind both the silent 5.3 auto-discard and the explicit 5.4 delete — the two paths differ only in whether a caller awaited `useConfirm()` first.
- `src/components/NoteCard.tsx` — the draggable note. Drag is plain pointer events on a small header strip only (not the whole card, unlike `BlockCard`), so the textarea underneath keeps normal text-editing pointer behaviour (click-to-place-cursor, selection) instead of fighting the drag handlers; position persists on pointer-up exactly like `BlockCard`. Content is local state, saved via `useUpdateNoteContent` on blur.
  - **The 5.3-vs-5.4 distinction** (the one open decision this phase resolved, see below): tracked with a `useRef<boolean>` per note, `hadContentRef`, initialised from whether the note already has content on mount and flipped permanently to `true` the first time the textarea's content becomes non-empty — it never flips back. On blur: content empty **and** `hadContentRef.current` still `false` → the note was never given real content, so it's deleted immediately with no confirm (5.3). Anything else — content present, or content now empty but `hadContentRef.current` is `true` — just saves, confirm-gated delete is the only way to remove it (5.4). This is exactly the client-state substitute for a "was ever non-empty" column, which the schema deliberately doesn't have.
  - Explicit delete (5.4) is a small "Delete" button in the header strip, gated by `useConfirm()` like every other delete in the app. It sits inside the same header as the drag handle, which surfaced a real bug during verification: the header's `setPointerCapture` (copied from `BlockCard`'s pattern) retargets *all* subsequent events for that pointer to the capturing element, including the button's own `click` — so clicking Delete never fired its handler at all, silently. Fixed by skipping `setPointerCapture` (and the whole drag) when the pointerdown's target is inside a `<button>`. Also guarded: a mousedown on Delete sets a `deletingRef` flag before the textarea's blur fires, so a click on Delete can never race with the 5.3 auto-discard path on the same note; if the confirm is cancelled, any pending content edit is saved instead of silently dropped.
- `src/components/Canvas.tsx` — added a "+ Note" button next to "+ Add block" in the toolbar. No popup: it calls `useCreateNote` directly, positions the note at the current viewport centre (same one-time-coordinate approach as 3.5, not an arrangement rule), and remembers the new note's id so its `NoteCard` renders with `autoFocus` on mount (5.1's "focused for typing"). Renders one `NoteCard` per Note from `useNotes(areaId)` alongside the existing `BlockCard`s (5.5 — both live on the same canvas, unrelated to each other).
- No new dependencies. No schema changes — the `notes` table already had everything 5.1-5.5 needed.
- Verified in a headless browser against a temporary in-memory mock of the Supabase client (written over `src/lib/supabase.ts`, restored before committing, same pattern as every prior phase), seeded with one Area: clicking "+ Note" created a row immediately (confirmed against the mock store, no popup ever rendered) and `document.activeElement` was the new note's `<textarea>`; typing "Hello world" and blurring (a click elsewhere) persisted that content to the mock store; dragging the header handle by (150, 100) moved the card on screen and persisted the new `x`/`y`; creating a second note and blurring it immediately with no typing removed it from the store entirely (5.3); creating a third note, typing "Temporary content", then selecting-all and deleting the text before blurring left the row in the store with `content: ""` — it survived (5.4, the critical case); creating a fourth note with real content and clicking its Delete button opened the confirm dialog ("Delete this note?"); Cancel left the note and its content untouched, and a subsequent Delete-then-Confirm removed it from the store. All of this was also screenshotted and visually inspected, not just asserted from store state — notes render as a small yellow card with a drag-handle/Delete header above the text area, multiple notes coexist and are independently draggable, and the confirm dialog overlays correctly. No console or page errors during any of this. **Not verified**: anything against a live Supabase project — this environment has no credentials, per the instruction not to seek any.

## Escalation criteria — Current v2

Always escalate:

* Anything touching the database schema or a migration. Phase 2b specifically: confirm the live backup exists before it runs, not just before the phase starts — this migration rewrites rows that are in real use, v1's did not.
* Anything not explicitly decided in spec or TASKS.md — no guessing at product intent. If something looks like it needs a new open decision beyond the three already resolved, stop and ask rather than picking a default.
* Anything touching auth. Current has its own dedicated Supabase project — no shared-project data boundary to worry about the way Overload's incident did.
* Diagnostic or live SQL queries run through the Supabase SQL Editor bypass RLS entirely — that's a property of the SQL Editor itself, confirmed on Overload, not something specific to Overload's schema. Current has no per-row user_id to filter by (RLS here is pinned directly to auth.uid()), so there's no WHERE-clause equivalent of Overload's rule. Prefer the authenticated client over the SQL Editor for diagnostic reads where that's an option. If the SQL Editor is used anyway and returns more than one account's data, that's still a bug — stop immediately, don't investigate further.
* The builder deleting or overwriting existing data or files unexpectedly during the build — not the app's own confirmed delete features, which are already fully specced.
* A test failure without an obvious, mechanical fix.
* Anything that would change scope, cost, or timeline versus TASKS.md.

Proceed without asking:

* Lint/type fixes, typos, formatting.
* Adding tests for already-specified behavior.
* Following a pattern already established elsewhere in the codebase.
* Anything TASKS.md's acceptance criteria already cover, including the two resolved decisions now patched into the file.

Note, unchanged from v1 and worth keeping verbatim: for schema and auth, "already decided" means the decision doesn't need relitigating — not that the implementation skips a look. Bring the actual diff every time. This is exactly how v1's RLS bug got caught.
